# 04 — Data Model

Postgres 16. Conventions: UUIDv7 primary keys (time-ordered → index-friendly), `created_at`/`updated_at` everywhere, soft-delete (`deleted_at`) on user-visible resources, every tenant-scoped table carries `org_id` with **Row-Level Security** enforcing `org_id = current_setting('app.org_id')` (set per-request/per-job; API-layer checks are the first line, RLS is the structural backstop).

## 1. Domain map

```
Org ─┬─ Users / Memberships (role)          Tenancy & access
     └─ Project ─┬─ Documents ─ Elements/Chunks       Ingestion
                 ├─ PipelineRuns ─ PipelineSteps      Orchestration
                 ├─ Entities ─ EntityRelations        Knowledge model (PKM)
                 │      └─ Evidence ──► Elements
                 ├─ ReviewItems                       Analyst loop
                 ├─ Opportunities ─ RoiModels         Analysis
                 ├─ Deliverables ─ DeliverableVersions Exports
                 ├─ AuditEvents                       Trust surface
                 └─ UsageEvents                       Cost metering
```

## 2. Core tables (abridged — authoritative DDL lives in Alembic migrations)

**Tenancy & access**
- `orgs(id, name, slug, settings jsonb, plan)`
- `users(id, email, name, workos_id, ...)`
- `memberships(user_id, org_id, role)` — role ∈ `org_admin | project_lead | analyst | viewer`
- `projects(id, org_id, name, industry_pack, status, settings jsonb)`

**Documents & ingestion**
- `documents(id, org_id, project_id, filename, mime, content_hash, blob_key, doc_class, pii_summary jsonb, status)` — `content_hash` powers dedupe + pipeline caching.
- `document_elements(id, document_id, kind, page, coords, section_path, text, table_json, order_key)` — the provenance atoms; `kind` ∈ heading/para/table/figure/diagram_shape. **Citations point here**, so elements are immutable once written.
- `chunks(id, document_id, element_ids uuid[], text, token_count, embedding vector, tsv tsvector, meta jsonb)`

**Pipeline orchestration**
- `pipeline_runs(id, project_id, kind, status, started_at, finished_at, error, trigger)` and `pipeline_steps(run_id, name, status, input_hash, output_ref, attempt, cost_tokens)` — idempotent resume: a step whose `input_hash` matches a prior success is skipped. This table pair is what makes Celery safe (docs/02 §3) and progress UI honest.

**Knowledge model (PKM)** — the heart of the product
- `entities(id, org_id, project_id, type, name, canonical_name, attrs jsonb, confidence, review_state, novel bool, version int)`
  - `type` ∈ `actor | system | process | process_step | business_rule | pain_point | risk | metric | compliance_item | ...` (extensible enum table, seeded per industry pack)
  - Modeling choice: **one entity table + typed `attrs jsonb` validated by per-type Pydantic schemas**, rather than a table per type. *Why:* extraction passes, review flow, evidence, and search treat all types uniformly (one join path, one review queue); per-type schemas still give strong typing at the application boundary. *Tradeoff:* no per-attribute DB constraints — accepted, since attrs are AI-populated and validated in code; anything relational (sequencing, ownership) is promoted to `entity_relations`, not buried in JSON.
- `entity_relations(id, project_id, from_id, to_id, rel_type, attrs jsonb, confidence, review_state)` — `rel_type` ∈ `performs | uses_system | precedes | hands_off_to | governed_by | causes | mitigates | ...` The process graph is `process_step` entities + `precedes`/`hands_off_to` relations — which is why swimlanes/BPMN are deterministic renderings (docs/03 §5).
- `evidence(id, claimable_type, claimable_id, element_id, quote, score)` — polymorphic link from any assertion (entity, relation, opportunity, roi assumption) to source elements. **Every AI assertion must have ≥1 evidence row or be flagged `estimate`.** Enforced in the write path, not by convention.
- `review_items(id, project_id, subject_type, subject_id, question, kind, status, resolved_by, resolution jsonb)` — the analyst queue: low-confidence assertions, entity-merge proposals, extraction questions. Resolutions append to the eval corpus.

**Analysis & deliverables**
- `opportunities(id, project_id, process_id, taxonomy_type, title, description, impact_score, complexity_score, risk_score, rationale, rubric_version, review_state)`
- `roi_models(id, opportunity_id, assumptions jsonb, computed jsonb, version)` — assumptions each carry `{value, unit, source: evidence_id | 'analyst' | 'estimate'}`; `computed` is regenerated by code from assumptions, never hand-written.
- `deliverables(id, project_id, type, title, status)` + `deliverable_versions(id, deliverable_id, version, spec jsonb, rendered_blob_key, citation_map jsonb, generator_version, created_by)` — `spec` is the structured content (sections, diagram JSON, tables); rendering to PPTX/DOCX/PDF is a pure function of `spec`. **Versions are immutable**; regeneration creates a new version → diffable deliverables, defensible history ("what did we show the exec committee in March").

**Trust & metering**
- `audit_events(id, org_id, actor_id, action, resource_type, resource_id, meta jsonb, ip, at)` — append-only (no UPDATE/DELETE grants), written via one `audit()` helper in the service layer. A product feature (visible to org admins), an enterprise checkbox, and cheap only if built now.
- `usage_events(id, org_id, project_id, kind, model, tokens_in, tokens_out, cost_usd, ref)` — per-call AI metering → per-project COGS.

## 3. Versioning strategy

Three different problems, three deliberate mechanisms:
1. **Documents** — new upload of same filename = new `document` row linked by `supersedes_id`; elements/chunks are per-document-version, so old citations never dangle.
2. **PKM entities** — current-state row + `entity_history` append (old values, change source: `pipeline|analyst`, timestamp). The model is a living current-state with history, not an immutable ledger — analysts edit it constantly and deliverables read "now."
3. **Deliverables** — fully immutable versions (above), because they're what leaves the building.

## 4. Search paths

- Semantic: `chunks.embedding` (pgvector HNSW, filtered by org/project/doc-class).
- Lexical: `chunks.tsv` GIN; fused with vector results (RRF) in the retrieval service.
- Structured: plain SQL over the PKM — the payoff of one database (docs/02 §4).

## 5. Migration & seed discipline

- Alembic, one migration per PR, `alembic upgrade` gates deploy; migrations must be reversible or explicitly marked destructive with a backup step.
- Seed sets: minimal dev seed (1 org, 1 project) and the **synthetic insurance corpus** (docs/03 §7) used by demos, integration tests, and evals — so no environment ever needs real customer data to be useful.
